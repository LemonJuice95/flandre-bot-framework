# CommandRunner对象复用池优化

## 优化背景

框架中的命令处理机制，会对每一条消息新建已注册的所有`CommandRunner`对象（下称“执行器对象”），这导致在消息较多时，执行器对象频繁被创建、丢弃，可能增大GC压力，显著增大Minor GC频率，甚至可能导致一些未被及时释放的执行器对象进入Old Gen，从而导致可能的Mixed/Full GC的触发

因此引入执行器对象复用池试图进行优化

## 优化价值测算

测试机配置，下同
> - CPU: AMD Ryzen 7 8845HS 3.80GHz 8核16线程
> - 内存: 英睿达 2 * 16GB DDR5 5600MHz
> - 系统: Windows 11 Pro 25H2

测试方式：
> 1. 构造可复用的消息池，消息长度最短为3消息段，最长为50消息段
> 2. 构造轻量匹配/重量匹配两类命令执行器，其中轻量匹配进进行一次普通的数据比对，重量匹配使用框架内的`MessagePattern`与`MessageMatcher`进行状态机匹配，使用特定方式确保最终匹配失败以保证每条消息稳定触发所有执行器对象的使用
> 3. 将每类执行器以1:1比例，共计100条注册到框架
> 4. 构造框架最小化启动序列，并启动
> 5. 从消息池中随机取用消息，以1000消息/s的速率将消息注入`CommandHandler`

测试发现在120s的测试时长内，Young GC总计触发120次，使GC共计从Eden Space回收了约70.9GB的对象，通过JMC分析JFR生成的文件发现，对象分配主要用于如下部分

> 1. 重量匹配执行器中`MessageMatcher`内部容器动态扩容时新的`HashMap$Node` `Object[]`等对象（内存占比最大）
> 2. 重量匹配执行器中`MessageMatcher`在进行匹配过程中产生的`State`对象
> 3. 执行器对象

上述对象分配中，1与3可以通过池化执行器对象以优化（1可以通过复用时重置旧有`MessageMatcher`，清空内部容器但保留相似匹配路径下的容量以优化），2则为算法正确性的保证，几乎无法进行优化

## 复用池实现

### 复用条件

框架将试图对每个被注册到框架的执行器类进行单独的池优化（为每个执行器类单独分配一个复用池），判断一个执行器类能否被池优化的依据为：
> 1. 类本身没有标注`@ForceNoPooling`注解
> 2. 继承链上所有类内部所有非`static`字段均带有`@Resettable`注解

若上述其中一条没有满足，框架将拒绝对该执行器类进行池优化

*注：`@Resettable`仅为契约，即**声明**该对象会在`free()`/`reset(Message)`方法中被释放/重置，具体清理逻辑仍需手动实现*

### 复用池模型与操作

复用池包含两个容量参数：初始容量与最大容量，基于实际情况对池进行动态扩容（不超过最大容量），并不进行缩容

对于初始容量，**不预先填充**执行器对象，而是在使用过程中惰性创建

复用池实现`ICommandRunnerPool`接口，暴露`take(Message)`与`put(CommandRunner)`两种方法

*（对于无法池优化的执行器类，使用`DummyCommandRunnerPool`以提供对应的空实现）*

对于`CommandRunnerPool`实现，采用`ArrayDeque`作为容器，该实现的对应方法操作如下：
- `take(Message)`方法
> 1. 试图从队列中取出执行器对象，如果成功取出，则使用`reset(Message)`重置该执行器对象的内部状态并返回
> 2. 若无法取出对象（队列为空），则判断能否在池中进行创建，判断依据为**池中当前已创建对象数**`size`是否小于**当前池容量**`capacity`
> 3. 若可在池内进行创建，则创建并返回该对象
> 4. 若无法创建，则记录一次miss并返回null，由上游自行降级（回退至创建使用完毕后立即丢弃的执行器对象）

- `put(CommandRunner)`方法
> 1. 使用`free()`方法释放该执行器对象的内部状态
> 2. 将执行器对象入队

### 自动扩容

在配置中给定miss率的扩容阈值，当一定时间窗口内的总体miss率超过阈值时，进行一次扩容，并在一定时间内不再扩容

时间窗口与扩容冷却的时长在框架的实现中均为40s，单次扩容将使池容量增长至当前的1.5倍（不超过最大容量）

扩容步骤：
> 1. 创建新的队列并分配计算得出的新容量
> 2. 将旧队列中所有的对象移至新队列中
> 3. 替换引用丢弃旧队列，使用新队列
> 4. 将新的容量写入`capacity`

miss率的统计方式：
> - 对每一次`take(Message)`记录一次`borrow`
> - 对每一次失败的`take(Message)`（最终返回null时）记录一次`miss`
> - miss率 = `miss` / `borrow`

*注：判断当前是否需要扩容的时机在此处每次进行记录之后*

滑动窗口实现方式：
> - 在统计中维护两个数组（`borrowBuckets`与`missBuckets`），每个数组包含8个桶，每个桶拥有5s的时间窗口
> - 维护两个整数`borrowCount`与`missCount`，用于表示当前整体窗口内的借出/miss计数
> - 对于每次借用记录（不论成功与否），使`borrowBuckets`的当前桶计数与`borrowCount`同时+1
> - 对于每次失败的借用记录，使`missBuckets`的当前桶与`missCount`同时+1
> - 在每次记录前，先判断当前时间是否超过了当前桶的失效时间，若超过，则按时间窗口推进对应数量的桶，将两个计数变量分别减去推进经过的对应桶计数之和

### 线程安全

上述操作中，需要考虑并发竞争的操作与解决方案如下：

- 队列操作：
> - 竞争原因：不同消息的命令执行为多线程并发，每条线程借用/归还执行器对象时需要保证队列状态的一致性
> - 方案：使用`ReentrantLock`对每次`poll()` `offer()`与扩容时的全量替换操作加锁
> - 方案采用原因：`ReentrantLock`在短临界区的存取操作时大概率使用自旋锁，理论上较难退避至入队后park（此处正确性有待考量），且队列操作中存在重量级操作（扩容），此时需要避免让借用者进行无意义的CAS自旋，并且引入更高级优化的成本过高，可能使代码复杂度达到无法维护的程度

- 进行能否在池内创建新对象的判断：
> - 竞争原因：每条借用线程中判断是否能够在池内创建新对象时，需要依据共享状态`size`，并需要在确认创建时写入`size`状态
> - 方案：使用框架内部实现的`OnlyCASLock`（纯CAS自旋锁）保护`size`状态，并在锁内外进行双重检查（分出快速路径）
> - 方案采用原因：需要在池内创建新对象的路径在池达到相对稳定后较低频，且框架中以使用`boolean`标志位分离“确认创建”与“创建”操作，将创建新对象这一昂贵操作移至锁外，锁内临界区极短，此时采用重量级锁将带来额外的挂起开销

- 统计中的数据记录：
> - 竞争原因：每个线程在借用时均会进行一次记录，写入共享的统计数据
> - 方案：采用同上的纯CAS自旋锁保护统计数据与桶切换操作
> - 方案采用原因：记录一次借用为高频路径且临界区同样极短（向基础类型变量写入数据），桶切换操作则相对低频，且临界区虽相比记录借用而言较长，但仍然只有数次基础类型的变量操作

## 优化后测试

### 瞬时爆发测试

*此处GC参数均使用JVM默认参数，堆大小参数为最小1024MB，最大2048MB*

- 测试方式：
> 1. 构造同上的执行器类与消息池，但加入一条消息处理完毕后使一个全局`CountDownLatch`进行倒计数的逻辑
> 2. 进行10万次随机消息抽取并注入`CommandHandler`
> 3. 记录在池化与非池化场景下的测试结果与gc日志

本次测试构造以下三种条件，每种条件各进行五次测试，平均数据如下：

|     优化方式      |  无池优化   | 框架默认参数池优化 | 初始大容量池优化 |
|:-------------:|:-------:|:---------:|:--------:|
|    对象池初始容量    |    -    |    10     |   500    |
|    对象池最大容量    |    -    |    50     |   500    |
|     扩容阈值      |    -    |    0.3    |    -     |
| 100K消息数处理时长均值 | 2864ms  | 2735.4ms  | 2653.6ms |
|   消息处理时长优化率   |    -    |  约4.50%   |  约7.35%  |
|    GC总次数均值    |  100.4  |   92.2    |    92    |
|   GC总次数优化率    |    -    |  约8.17%   |  约8.37%  |
|  GC总回收量估算均值   | 59.14GB |  54.20GB  | 54.08GB  |
|   GC总回收量优化率   |    -    |  约8.35%   |  约8.56%  |

- 结论
> - 使用池优化后，各项数据均有所降低，表明**优化存在正向收益**
> - 另外，在此数量级的并发下，使用对象池时性能仍然没有明显下降，表明上文中提到的**队列操作锁不构成性能瓶颈**

- 测试缺陷分析
> - 本测试采用瞬时爆发的策略对于池优化而言存在劣势，原因为对象池需要一定的时间进行动态调优，需要对象池内部在一定时长的运行后达到相对稳定的状态，方可发挥出最佳性能
> - 因此需要进行时长更长、消息注入速率更加稳定的测试
> - 但根据目前的测试数据，理论上长线测试很可能使最终计算的优化率更高
